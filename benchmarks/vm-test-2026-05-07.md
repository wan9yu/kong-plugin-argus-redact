# VM integration test — 2026-05-07

End-to-end validation of `argus-redact-bridge` on a clean Ubuntu 22.04 (aarch64) VM, isolated from the developer machine. Five scenarios run against a self-built docker-compose stack; one scenario swaps the mock LLM for a real OpenAI-compatible provider.

## Environment

- **Host**: Ubuntu 22.04 LTS aarch64 (Parallels VM on Apple Silicon, kernel 5.15)
- **Docker Engine**: 29.1.3
- **Docker Compose plugin**: v5.1.3
- **Stack**: `kong:3.7.1-ubuntu` (DB-less), argus-redact 0.6.4 from PyPI in `--insecure` demo mode, mock LLM (FastAPI). One scenario points the upstream at `https://api.deepseek.com` instead of the mock.

## Scenarios

### 1. README quickstart curl, verbatim

The exact `curl` from the README's `60-second demo` section, run unmodified:

```bash
curl -s localhost:18000/v1/chat/completions -H 'Content-Type: application/json' \
  -d '{"model":"gpt-4","messages":[{"role":"user","content":"我叫王五，手机13812345678"}]}' | jq
```

Result:
- Client received `"echo: 我叫王五，手机13812345678"` — original PII restored.
- Mock LLM logged `MOCK_LLM_REQUEST_BODY: {... "我叫傻大姐，手机19999173649" ...}` — only the pseudonymized form crossed the wire upstream.

### 2. Real LLM upstream

Kong reconfigured to forward to `https://api.deepseek.com` (an OpenAI-compatible chat endpoint reachable from China without VPN). The same payload, with `Authorization: Bearer $DEEPSEEK_API_KEY` and `model: "deepseek-chat"`, was sent. The user message instructed the model to echo verbatim.

Result: HTTP 200; client received `"我叫王五，手机13812345678"`. The LLM echoed the pseudonyms it was given (it never saw the real PII), and the plugin's local restore mapped them back to the original PII before the response left Kong. The argus-redact container's stdout shows a `POST /redact 200 OK` for the access-phase call.

The architecture under test (Kong + plugin + sidecar) is identical regardless of which OpenAI-compatible upstream is configured; the choice of DeepSeek for this run was driven by the test environment's network reachability constraints (the VM had no VPN; some other LLM endpoints were not directly reachable from inside the Kong container).

### 3. Plugin disabled — gateway still works

The plugin block was removed from `kong.yml`, leaving only the Service + Route. Kong was restarted. A request with PII was sent.

Result: HTTP 200; the mock LLM saw the original PII unchanged (expected — there was no plugin to redact); the response came through unmodified. Removing the plugin does not break Kong's proxy path; this confirms the plugin handler does not introduce side effects that persist beyond its own configuration.

### 4. No-PII request overhead

Two payloads were timed against the same stack with N=50 each, after a 5-request warmup:

| Payload | p50 | p95 | p99 | min | max |
|---|---|---|---|---|---|
| With plugin, no PII (`"What is 2 plus 2?"`) | 1.50 ms | 1.99 ms | 2.20 ms | 1.23 ms | 2.20 ms |
| With plugin, with PII (Chinese phone + name) | 1.75 ms | 2.05 ms | 2.32 ms | 1.40 ms | 2.32 ms |
| Baseline (plugin disabled, same payloads) | ~0.92–1.03 ms | ~1.40 ms | ~1.62 ms | 0.67 ms | 1.62 ms |

**Plugin overhead at p50 is ~0.5–0.8 ms** in steady state. The plugin path runs whether or not the message contains PII (the `/redact` HTTP call happens regardless, and argus-redact returns the original text plus an empty key map for clean inputs), so the overhead profile of a no-PII request is essentially the same as with-PII. This is by design — the plugin trusts argus-redact to decide what is PII rather than pre-filtering on the Lua side.

### 5. Bench reproduction (`scripts/bench.sh`)

The committed bench script run against the VM stack (with plugin, with-PII payload, N=100, 5-request warmup):

| Metric | Value |
|---|---|
| Total time | 0.51 s |
| Throughput | 195.9 req/s |
| p50 | 1.8 ms |
| p95 | 2.6 ms |
| p99 | 42.4 ms |
| min | 1.4 ms |
| max | 42.4 ms |

The single `max=42.4 ms` outlier on N=100 is consistent with occasional GC or scheduling jitter inside one of the containers; it does not appear at smaller N (Test 4 above) and is not reproducible at the same offset across runs.

## Findings worth surfacing

### Cold-start tax

Without the warmup loop, the first few requests after the argus-redact container starts are dramatically slower than steady-state. Measured without warmup, N=30:

| Metric | Value |
|---|---|
| p50 | 2.05 ms |
| p95 | **1105 ms** |
| p99 | **4053 ms** |
| max | 4053 ms |

The tail is the cost of argus-redact's first-time Python imports and regex compilation under load. A production deployment should warm the sidecar — a single dummy `/redact` call after start, or an initialization healthcheck that exercises the path — before serving real traffic. v0.1 ships without an automated warmup hook; this is a known gap.

### Native Linux is significantly faster than macOS Docker Desktop

The README's headline performance numbers on Apple M1 Max + Docker Desktop (`p50 6.6 ms`, `p95 10.8 ms`, `42.4 req/s`) are roughly **3–4× slower** than the same plugin code, same images, on native Linux (`p50 1.8 ms`, `p95 2.6 ms`, `195.9 req/s`). The difference is Docker Desktop's hypervisor and bind-mount overhead on macOS, not the plugin. Production deployments on Linux nodes should expect numbers closer to the Linux row.

## Cleanup

Test workspace: `~/argus-test/` on the VM (rsynced repo at `~/argus-test/repo/`, ephemeral API keys at `~/argus-test/.poe_key` and `~/argus-test/.deepseek_key`, mode 600).

The VM's Docker daemon was temporarily configured with an HTTP proxy in `/etc/systemd/system/docker.service.d/http-proxy.conf` for image pulls (the test network had limited direct-egress). This is a per-host setup, not part of the plugin's deployment requirements; remove it before the proxy is decommissioned to avoid future image-pull failures.
